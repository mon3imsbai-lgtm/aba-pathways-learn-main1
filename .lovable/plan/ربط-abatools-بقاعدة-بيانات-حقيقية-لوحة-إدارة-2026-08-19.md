# ربط AbaTools بقاعدة بيانات حقيقية + لوحة إدارة

## 1) نتائج تحليل المشروع

الموقع اليوم بالكامل **ثابت (Static)**: كل البيانات مكتوبة داخل ملفات React كمصفوفات.

| الصفحة | البيانات الحالية | القرار |
|---|---|---|
| `/courses` | مصفوفة 9 مسارات (عنوان، وصف، ساعات، حالة) | ديناميكي |
| `/courses/abat` | محتوى مفصّل في `src/lib/abat-content.ts` (11 مجال منهج، معايير تقييم، سياسة الطعن) | يبقى ثابتاً (محتوى تحريري طويل نادر التغيير) مع ربط بيانات الدورة نفسها بالقاعدة |
| `/shop` | 8 منتجات رقمية بسعر MAD + زر "أضف للسلة" غير فعّال | ديناميكي |
| `/resources` | 8 موارد (نسخة مكررة من المنتجات) | ديناميكي — نفس جدول المنتجات، بدون تكرار |
| `/blog` | 6 مقالات (عنوان، مقتطف، تاريخ، كاتب) | ديناميكي |
| `/services` | 6 خدمات بأيقونات | ديناميكي (اسم الأيقونة يُخزَّن كنص) |
| `/pricing` | باقة ABAT 1000 MAD | ديناميكي (سعر الدورة داخل جدول الدورات) |
| `/contact` | نموذج لا يحفظ شيئاً | يُحفظ في القاعدة |
| `/refund-policy` | نموذج بنكي (RIB، البنك، صاحب الحساب) لا يحفظ شيئاً | يُحفظ في القاعدة كبيانات حساسة |
| `/auth` | تسجيل دخول بالبريد موجود مسبقاً (يخدم MCP OAuth) | يُعاد استخدامه |
| الهيدر/الفوتر/التصميم | ثابت | لا يتغيّر إطلاقاً |

الثابت الذي يبقى في الواجهة: النصوص التسويقية، الصور، الهوية البصرية، بنية الصفحات، محتوى ABAT التحريري.

## 2) بنية قاعدة البيانات المقترحة (Supabase — الخيار الأنسب لأنه مفعّل أصلاً في المشروع ويوفّر Auth + RLS + Storage)

الكيانات المكتشفة: مسار تدريبي، خدمة، منتج رقمي، مقال، رسالة تواصل، طلب استرجاع، مستخدم، دور.

```text
profiles ──1:1── auth.users
user_roles (admin | editor | user)

courses      (slug, title, subtitle, description, hours, price_mad, level,
              delivery_mode, status[soon|open|closed], is_featured,
              cover_url, sort_order, is_published)
              └── course_modules (course_id, title, description, sort_order)

services     (slug, title, description, icon, audience, sort_order, is_published)

products     (slug, title, description, price_mad, cover_url, file_path,
              product_type[ebook|worksheets|cards|toolkit], is_free,
              show_in_resources, sort_order, is_published)
              └── product_categories (many-to-many عبر product_category_links)

blog_posts   (slug, title, excerpt, content, cover_url, author_name,
              author_id → profiles, published_at, is_published)

contact_messages (name, email, request_type, message, status[new|in_progress|done])
refund_requests  (full_name, email, registration_ref, bank_name,
                  account_holder, rib, reason, status[pending|approved|rejected|paid])
```

العلاقات: `courses 1—N course_modules`، `products N—N product_categories`، `blog_posts N—1 profiles`، `user_roles N—1 auth.users`.

قابلية التوسع لاحقاً بدون إعادة بناء: التسجيل في الدورات (`enrollments`)، الطلبات والدفع (`orders`/`order_items`)، تحميل الملفات المشتراة، تعدد اللغات عبر حقول `*_en`، تصنيفات المدونة.

## 3) الأدوار والأمان
- `user_roles` في جدول منفصل + دالة `has_role()` من نوع SECURITY DEFINER (لا تُخزَّن الأدوار في `profiles`).
- RLS مفعّل على كل جدول:
  - قراءة عامة (`anon`) للمحتوى المنشور فقط: `is_published = true`.
  - كتابة/تعديل/حذف: للمدير فقط.
  - `contact_messages` و`refund_requests`: `INSERT` مسموح للجميع، **القراءة للمدير فقط** (بيانات بنكية حسّاسة).
- `GRANT` صريح لكل جدول، لا استخدام لمفتاح الخدمة في الواجهة.
- تخزين الصور والملفات في Storage: bucket عام `media` للأغلفة، وbucket خاص `product-files` للملفات القابلة للتحميل.

## 4) الربط بالواجهة (بدون أي تغيير في التصميم)
- دوال `createServerFn` عامة للقراءة (SSR + SEO محفوظ) في `src/lib/content.functions.ts`.
- كل صفحة تستبدل مصفوفتها المحلية بنفس شكل البيانات القادمة من القاعدة — نفس الـ JSX والكروت والألوان حرفياً.
- نموذجا التواصل والاسترجاع يحفظان فعلياً مع رسائل النجاح الحالية نفسها.
- بيانات أولية (Seed) في نفس الترحيل تطابق المحتوى الظاهر اليوم، فلا يتغيّر شيء بصرياً.

## 5) لوحة الإدارة `/admin` (محمية بدور admin)
- نظرة عامة + إدارة: الدورات ووحداتها، الخدمات، المنتجات/الموارد، المقالات، رسائل التواصل، طلبات الاسترجاع.
- لكل قسم: إضافة، تعديل، حذف، نشر/إخفاء، ترتيب، ورفع صورة.
- التصميم يعتمد نفس نظام الألوان والخطوط والكروت الحالية.

## 6) التحقق
بناء ناجح، فحص RLS، واختبار عبر المتصفح لكل الصفحات العامة + دخول المدير + عمليات CRUD.
